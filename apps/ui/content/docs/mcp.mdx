Point any MCP client at the registry and it gets metagraphed as callable tools: subnet discovery and comparison, per-subnet health and economics, OpenAPI schemas for every registered subnet API (callable through the registry itself), chain blocks/extrinsics/events, account lookup, and grounded question-answering — the same data every REST route serves, shaped for agents. Bittensor in a box: one connect, no key, no account, no local install.

## Which endpoint

**Default to `/mcp`.** It advertises four discovery tools: `search_tools`, `invoke_read_tool`,
`invoke_tool`, and `get_more_tools`. Your client loads complete tool definitions as needed instead
of putting the full catalog into chat context at connection time.

| Endpoint            | Initial listing                      | Choose it when                                          |
| ------------------- | ------------------------------------ | ------------------------------------------------------- |
| `/mcp`              | Four discovery and invocation tools  | You want a small initial catalog and task-based search. |
| `/mcp/core`         | Common tools, directly advertised    | Your client needs the common tools listed up front.     |
| `/mcp?catalog=full` | Every tool with its complete schemas | Your integration requires an eager catalog.             |

Every profile can call every tool with the same authentication, permissions, and limits.
Selecting a smaller listing does not change an individual tool's schema or result.

`search_tools` accepts task keywords or an exact tool name and returns up to three complete
matching definitions. Each includes the input and output schemas, annotations, and authentication
requirements. Follow `next_cursor` with the same query to see more matches. Search by exact name
when you already know the tool you need, so unrelated schemas do not enter the conversation.

For a tighter per-response budget, configure `https://api.metagraph.sh/mcp?search_page_size=1`
(or `2`). This optional setting keeps the initial catalog unchanged and returns at most one
(or two) complete matching definitions per search page. The default remains three. Following
all pages can require more requests; individual schemas and target results stay complete.

Clients that only allow advertised tools can use `invoke_read_tool` for a discovered tool with
`readOnlyHint: true`, or `invoke_tool` for other targets. Both validate the target's arguments and
apply its permissions. If a definition says authentication is required, sign in before calling it.

`get_more_tools` records a missing capability. Use it only when the catalog cannot do what you
need and describe the goal in `context`; it acknowledges the gap rather than returning extra tools.

## Authentication

Optional. Anonymous access works on every profile at 100 requests/60s per client IP. Clients that support MCP authorization prompt an OAuth sign-in (GitHub) on first connect; an `Authorization: Bearer mg_…` [API key](/settings) header works too. Authenticating raises rate limits (500 requests/60s per account, higher on paid tiers) — it does not unlock additional tools or surfaces.

## Connect a client

### Claude Code

One CLI command, no config file to hand-edit:

```bash
claude mcp add --transport http metagraphed https://api.metagraph.sh/mcp
```

### Claude Desktop & claude.ai

Both take the endpoint as a custom connector: **Settings → Connectors → Add custom connector**, then paste `https://api.metagraph.sh/mcp`. Claude Desktop also accepts a config-file entry:

```json title="claude_desktop_config.json"
{
  "mcpServers": {
    "metagraphed": {
      "transport": { "type": "http", "url": "https://api.metagraph.sh/mcp" }
    }
  }
}
```

### Cursor

```json title=".cursor/mcp.json"
{
  "mcpServers": {
    "metagraphed": { "url": "https://api.metagraph.sh/mcp" }
  }
}
```

### VS Code

```json title=".vscode/mcp.json"
{
  "servers": {
    "metagraphed": { "type": "http", "url": "https://api.metagraph.sh/mcp" }
  }
}
```

### Any other client

Any client that speaks streamable-HTTP MCP connects directly — no install, no key:

```json title="Generic streamable-HTTP entry"
{
  "type": "streamable-http",
  "url": "https://api.metagraph.sh/mcp"
}
```

## First calls to try

Start with discovery, then invoke the selected tool using the complete arguments its schema requires:

| Goal                             | `search_tools` query  | Next step                                                                             |
| -------------------------------- | --------------------- | ------------------------------------------------------------------------------------- |
| Find inference subnets           | `search_subnets`      | Pass the search query to the discovered read-only tool through `invoke_read_tool`.    |
| Ask a grounded registry question | `ask`                 | Follow the returned schema to ask the question through `invoke_read_tool`.            |
| Call a subnet's registered API   | `call_subnet_surface` | Discover the API and required arguments, then choose the bridge from its annotations. |

Keep tool discovery specific to the current task. A broad query can match many tools; load another
page only when the current definitions do not cover what you need. API schemas and tool responses
remain complete, so select supported filters and bounded pagination instead of asking for every
record at once.

Every tool mirrors a documented REST route — the [API reference](/docs/api-reference) covers the request/response shapes behind them, and [For agents](/agents) has the rest of the machine surface: playbooks, `llms.txt`, the served skill, and prompt-ready links.
