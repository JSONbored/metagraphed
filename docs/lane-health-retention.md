# Bounded health trigger migration candidate

The compatible runtime from merged PR #12721 checks six actual SQLite trigger
definitions before D1 health housekeeping. This schema candidate promotes its
reviewed test fixture, without changing the SQL bytes, to the canonical
`migrations/d1/0039_lane_health_retention_trigger_bounds.sql`. Existing regressions
now read that migration directly; no second SQL copy remains.

This is source preparation only. No merge, production application, schema capture,
cleanup, credentials change or deployment is authorized by this candidate.

## Exact behavior and current limits

The migration drops three old triggers and creates five definitions using existing
indexes. It changes no history row, projection row, table, column or index directly.
The existing current-row delete trigger is unchanged. All six definitions then match
the runtime readiness hashes, so a fresh selected D1 health store enables existing
housekeeping on natural write attempts immediately. There is no release flag.

Health expiry keeps its strict 90-day cutoff, all latest timestamp ties, and at most
20 direct deletions per attempt. Failed or ambiguous inserts retain their original
acknowledgement and are never replayed. A store that previously cached false stays
disabled for that request; the next store checks actual metadata again. PostgreSQL
and the already-published, independently bounded burn retention are unchanged.

The separately authorized live read on October 19, 2026 found exactly 38 recorded
migration filenames through `0038_raw_capture_publications.sql`, with source filename
parity and no duplicates or extras. Of the six required health triggers, two were
missing, three differed and one matched. The exact existing health-expiry eligibility
count was **zero**. This repair therefore cannot reclaim current health capacity;
DDL may still require allocation in a near-full database. It does not authorize
shorter retention, a bulk drain or any unrelated deletion.

## Automatic application and merge effects

The migration and physical snapshot paths match the existing D1-maintenance push
filter. A main merge automatically runs `npm run migrate:d1 -- --remote`, applying
**every** pending tracked migration before ledger and physical-schema verification.
The generated snapshot matches production build paths for the API, data API and
registry-sync API. It does not match WSS-LB's production paths. Those three builds
and contract sync run independently. No private Container publication is part of
this PR. A check failure after application does
not establish DDL rollback or authorize a blind retry.

Consequently this is not a dormant main merge: application enables the existing
health expiry described above. A schema-branch application through native D1
maintenance would have that same immediate effect before any merge. Both require
separate exact approval and fresh pending-file, store-identity, capacity and runtime
compatibility evidence. The October 19 read is evidence for preparation, not a
permanent current-ledger receipt.

After an approved application, verify the actual six definitions, complete ledger
and steady physical schema against the candidate artifacts. Do not call prospective

unbounded cleanup; selected percentages alone do not prove native quiescence.
