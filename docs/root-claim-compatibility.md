# Legacy Root-claim compatibility

`GET /api/v1/accounts/{ss58}/root-claim` and MCP `get_account_root_claim` describe the retired per-subnet claim system. They do not describe current Root basket holdings, beta shares, owed entitlement or a claim quote. The existing GraphQL field uses the same loader during its planned retirement; this change adds no query or transaction operation.

The reader obtains a finalized block hash and calls `state_getRuntimeVersion` at that hash before consulting its KV cache. Supported storage reads use that same hash, so an upgrade between requests cannot mix legacy storage with a newer runtime. Compatibility is evaluated independently for each requested network.

| `compatibility.status` | Meaning                                                                                               | Claim fields                                                                    |
| ---------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `legacy_supported`     | Audited `node-subtensor` spec 440; all bounded reads decoded successfully                             | Legacy claim mode and hotkey entries, possibly an explicitly empty list         |
| `unsupported`          | `node-subtensor` spec 441 or later; Root Reborn retired the old claim path                            | Both `claim_type` and `hotkeys` are null; no legacy storage requests are issued |
| `unavailable`          | Unknown runtime, failed/malformed response, or a legacy hotkey list exceeding the 64-entry read bound | Both fields are null; this does not imply zero entitlement                      |

`reason` distinguishes `root_reborn`, `unverified_runtime`, `rpc_or_decode_failure` and `legacy_limit_exceeded`. The compatibility object also supplies the observed spec name/version and finalized block hash when available. A supported `claim_type_source` identifies an explicit `storage` value versus a proven `runtime_default`; it is null for unsupported or unavailable responses. `queried_at` remains the time the cached record was assembled.

The spec-440 adapter applies its verified ValueQuery defaults only after runtime support is established: missing claim mode means `Swap`, missing hotkey vectors/claimable maps are empty, missing claimed watermark is zero, and the missing claim threshold is **500,000**, not zero. Explicitly encoded zero thresholds remain zero. These are legacy raw accounting values, not a basket NAV or return calculation. A malformed or absent JSON-RPC `result` is a read failure; it is never treated as an unset storage key. The raw SCALE decoders themselves return null for absent input.

The KV namespace is `root-claim:v2:<ss58>` (with the existing network prefix). Pre-fix entries are excluded, and cached records from another observed runtime identity are rejected. Positive/unsupported records retain the 120-second TTL. The inherited 10-second negative-cache configuration is below [Cloudflare KV’s 60-second minimum](https://developers.cloudflare.com/kv/api/write-key-value-pairs/); unavailable records therefore must not rely on successful KV persistence. Correcting that shared cache policy is tracked separately in [#12052](https://github.com/JSONbored/metagraphed/issues/12052). A valid cached record can describe an earlier finalized block within that TTL. HTTP cache policy also remains bounded by the route's existing short cache profile.

## Source and adapter boundary

This compatibility matrix is pinned to source revisions, with synthetic encoded fixtures in tests; no production RPC or signed transaction was used for verification.

- [v440 runtime identity](https://github.com/RaoFoundation/subtensor/blob/e4ffa2e1325c6c7db618dbceaf396310a170990c/runtime/src/lib.rs#L230), [legacy storage definitions](https://github.com/RaoFoundation/subtensor/blob/e4ffa2e1325c6c7db618dbceaf396310a170990c/pallets/subtensor/src/lib.rs#L2732), [claim-mode default](https://github.com/RaoFoundation/subtensor/blob/e4ffa2e1325c6c7db618dbceaf396310a170990c/pallets/subtensor/src/lib.rs#L415), and [threshold default](https://github.com/RaoFoundation/subtensor/blob/e4ffa2e1325c6c7db618dbceaf396310a170990c/pallets/subtensor/src/lib.rs#L485).
- [v441](https://github.com/RaoFoundation/subtensor/blob/8b9d55c723e00d0d713eed799de627e94603dfd4/pallets/subtensor/src/lib.rs#L2788) removes `RootClaimType` and marks the old `RootClaimable` / `RootClaimed` storage as migration-only. The remaining threshold is consulted only at Root for fund-level claims.
- The same migration-only boundary is present in [v450](https://github.com/RaoFoundation/subtensor/blob/9540b3af59179b88af99f8e0d03add5d96512e3f/pallets/subtensor/src/lib.rs#L2965), [v453](https://github.com/RaoFoundation/subtensor/blob/823bdcbc58a29f60b243be4737a7c72b34ac7d93/pallets/subtensor/src/lib.rs#L2965) and [v454](https://github.com/RaoFoundation/subtensor/blob/14cde6410fe8ec81a940e290c56f94a632a0988d/pallets/subtensor/src/lib.rs#L2963).

The endpoint has no historical block parameter. Additional pre-440 or independently versioned runtime adapters require their own proven layout/defaults and archive-state tests. They are unavailable here rather than guessed from a version range. Native basket discovery, positions and claim data require separate contracts and complete ingestion; no replacement API URL is advertised until that surface exists. An unsupported legacy response must not be used to conclude that an account has no accrued basket entitlement.
